- Cross-platform matching per room lives in src/lib/room-reconcile.ts (pure, tested) and runs after every calendar sync; nameless entries overlapping a real stay on another platform are stored as blocked mirrors (bookings.mirror_of), named overlaps become flagged. Why: hosts without a channel manager link calendars to each other, so one stay shows up on several feeds.
- Every outside integration (ID reading, host email, guest messages) has a per-host demo/live switch in hosts.integration_modes (src/lib/integration-modes.ts); server code checks it before calling out. Why: the host tests each connection safely before going live.
- Contra is gone. Tradespeople come from the host's own contacts (trades table) and the local directory in src/lib/trades.ts: each card opens a web search limited to that site with the job and area, plus a link to the site itself (tests/trades-directory.test.ts). Why: most directories have no free-text search URL and several block automated checks, so site searches are the links that reliably work.
- Guest requests, host jobs and maintenance share one table, service_jobs; guest ETA updates are rows in messages (channel stay_page). Why: one inbox and one status flow for all work.
- Property theme lives in properties.theme_config, normalised by src/lib/theme.ts and applied via ThemeScope (CSS variables); vanity links /$slug reuse properties.short_code. Why: one source of truth per tenant, safe against bad input.
- Stay guides reuse guides/guide_steps: one guides row per (property, room or null, section_key); room rows override house rows; merging, basic/detailed, the forget card and link window are pure in src/lib/guide.ts (tested). Photos live in the private "guides" bucket as paths and are shown via short-lived signed links. Why: write shared sections once, keep guest photos private.
- Guide links are stay_tokens with valid_from (arrival-day midnight, property time) and expires_at (check-out time); hosts mint fresh ones from the booking window since only hashes are stored. Why: late arrivals need "Getting in" before self check-in.
- Booking sites: built-in channel ids never change; hosts add sites in hosts.booking_sites ([{key,label,icon_url}], icons are 64px PNG data URLs) and a stay or calendar link from an added site is channel "other" plus site_key. Use platformKey()/toChannel()/resolveSites() from src/lib/booking-sites.ts (tested). Why: no enum change, and icons work offline on a kiosk.
- Who's staying: properties.guest_records (normalised in src/lib/guest-records.ts, tested) controls asking adults/children, checking every adult's photo ID, keeping a small ID copy and face photo, and keep days (7/14/30 after check-out). Photos are only kept once the host confirms regulator (ICO) registration. One guest_ids row per person (position 0 = lead booker, children age only); small JPEGs live in the private "guest-ids" bucket (created on first use) and are shown via 10-minute signed links; purged daily by purgeGuestIds. Why: host security record without keeping full-size ID images.
- Server code reading columns from the newest migration wraps the query in withLegacy() (src/lib/checkin.server.ts) so check-in and the dashboard keep working until Lovable applies the migration.
- UK guest register (Immigration (Hotel Records) Order 1972) lives in guest_register, rules in src/lib/hotel-register.ts (tested): everyone 16+ gives full name and nationality; "aliens" (not British, Irish or a Schedule 3 Commonwealth country, BNA 1981) also give document number, place of issue and next destination. Kept 12 months from arrival (keep_until, purged daily), independent of the 7/14/30-day ID photo setting; entries survive deleting the stay or property (booking_id/property_id set null, names copied). Always on for properties with country_code GB; hosts view, export, print and correct it at /app/register. Why: legal record that must be open to inspection.
- Invoices (direct stays only) live in invoices, rules in src/lib/invoice.ts (tested: tax terms per country, totals, numbers). Nothing is generated until the guest (guest guide, via stay token) or host (guest card) asks; numbers come from claim_invoice_number() so they run in sequence per host. A guest may set email and postal address once, then it's locked to them; hosts can amend any field. Each invoice has an access_token link to /invoice/$token, a printable page whose "Download PDF" is the browser's Save as PDF. Why: keeps any alphabet intact without a PDF font dependency, and the same link is what guests share or email.
- Every change adds an entry to src/content/changelog.ts (newest first; kind new / improved / fixed, plus an area). The About page (/about, linked from the menu) shows it as "What's new", and its "new" items make up "All features". tests/changelog.test.ts checks versions and dates. Why: one list keeps the change log and features log in step.
- "/" sends signed-in owners and managers to /app/today; links that should show the home page use ?home=1 (the logo, Home, Pricing). The dashboard's chosen property is shared through useSelectedProperty (localStorage plus a window event), so menus and pages switch together.
- Free trial (/start) uses Supabase anonymous sign-in: the visitor gets an anonymous session, gives name and email first in /app/setup (saved to user_profiles and hosts.contact_email, so the lead is kept), sets up property and rooms, and later TrialBanner calls auth.updateUser({ email }) so the same user becomes permanent after the emailed link. If anonymous sign-ins are switched off, /start falls back to /auth?mode=sign_up. Why: no sign-up form before the host has seen value.
- Billing (migration 0024, src/lib/billing.ts tested, billing.functions.ts): hosts.subscription_status trialing/active/past_due/canceled/comped with trial_ends_at set on creation from platform_pricing.trial_days. host_has_access() gates can_write_host(), so every write policy and the read-only trigger stop changes when access ends; reads stay open, and guests' ID records, the register and invoices use can_read_private() so owners keep them. Checkout (mode subscription, trial_end = trial end when 48h+ away) collects the card; the Stripe webhook keeps status in step; cancelling deletes the Stripe subscription and ends access immediately. protect_billing_fields() stops owners editing billing columns. Why: no free use beyond the trial.
- Super admin = a confirmed email in public.super_admins (is_super_admin()). is_host_member() includes them (read everywhere); writes need support_can_write(), i.e. the owner's hosts.support_access_until (max 30 days, owner-only toggle). The admin page is /app/admin; "view as host" sets user_prefs.support_host_id, which getWorkspace honours. Trial-abuse triggers write trial_flags on a repeated address or contact email.
- Guest card payments use Stripe Connect (migration 0025, payments.functions.ts): each host links a Standard account (created with their email, finished on Stripe's hosted onboarding via account_links); Checkout sessions are direct charges with the Stripe-Account header, and requests.stripe_account_id records which account took each payment. hosts.uses_platform_stripe (super-admin-only) keeps a business on Latchkey's own account, set for the super admin's businesses. The platform account otherwise only collects subscriptions. Webhook accepts STRIPE_WEBHOOK_SECRET and STRIPE_CONNECT_WEBHOOK_SECRET; account.updated marks hosts ready. Why: hosts are paid directly and own their refunds and disputes.
- Bookings list (src/lib/booking-list.ts, tested): stays are grouped (here, arriving, leaving, upcoming, attention, past, cancelled, closed) for the default "smart" order; columns sort both ways with the smart order breaking ties; show/hide filters for groups, rooms and platforms are kept in localStorage, with past stays hidden by default. Why: hosts look for what's happening now first.
- Super admins are managed in the app (Latchkey admin → Site settings → Super admins); the database refuses to remove the last one. All Latchkey-wide settings (pricing, site settings, per-night invoice lines) live only in Latchkey admin, which the menu shows under Settings for super admins.
- The API and MCP server are generated from one spec, src/lib/api-spec.ts (operations, params, examples); REST (/api/public/v1), MCP (/api/public/mcp), OpenAPI and the /developers page all read it, and handlers live in src/lib/api-handlers.server.ts. Why: add an operation once and every surface and the docs stay in step.
- Anything that spends Lovable Run credits is listed in src/lib/jobs.ts, checked with jobAllowed() and counted with bumpUsage() into usage_daily (src/lib/usage.server.ts); the super admin switches and schedules them in job_settings. Why: the super admin decides what may run.
- Plans live in site_settings.pricing_model and only apply once the super admin publishes them in the pricing studio (pure maths in src/lib/pricing-model.ts, tested); until then the old platform_pricing per-room price applies. Why: prices never change by accident.
- Visitor analytics: the browser sends page views to /api/public/track (VisitTracker, honours GPC/DNT and ?notrack=1); people are matched deterministically in the database (analytics_identify: user id and email hashes, merge into the oldest profile, never on a shared demo account); summaries are pure in src/lib/analytics.ts. Kept 13 months, IPs cleared after 90 days. Why: CDP-style profiles without guessing.
- Launch offers (migration 0029, src/lib/offer.ts tested): the campaign lives in site_settings.offer (super admin, Pricing studio). The lock_in_offer trigger copies it onto hosts.offer_pence when an account is opened during the campaign. Checkout and price updates charge nextMonthPence() while the offer is pending; when Stripe reports the subscription active (first paid month), applyStripeSubscription sets offer_used_at and moves the subscription to the standard price from the next bill. Why: free trial → one offer month → standard, without relying on Stripe coupon timing around trials.
